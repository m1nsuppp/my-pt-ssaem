# AI 결정을 LLM과 결정 엔진의 하이브리드로 분리

도메인 결정을 세 레이어로 나눠, 정책(LLM)/계산(엔진)/표현(LLM)으로 책임을 분리한다. 모든 결정을 LLM에 맡기면 비결정적이고 디버깅이 불가능하며, 모든 결정을 엔진에 두면 유연성이 사라진다.

## 결정

모든 인-세션 결정은 다음 흐름을 따른다:

```
[입력] → [Layer 1: Policy (LLM)]
            "이번에 뭘 할지" 결정 (덜로드? 운동 교체? 무게 조절?)
         → [Layer 2: Calculation (결정 엔진)]
            "정확히 몇 kg / 몇 회" 산출 (룰 기반, 테스트 가능)
         → [Layer 3: Expression (LLM)]
            위 결정을 사용자 페르소나로 말하기
         → [출력]
```

### 각 레이어의 책임

**Layer 1 — Policy (LLM)**
- 컨디션/이력/트렌드를 보고 "이번 세션의 큰 방향"을 정함
- 예: "RPE 9가 3세트 연속 → 델로드", "정체 3주 → 운동 교체"
- 자연어 추론이 필요해 LLM이 담당

**Layer 2 — Calculation (결정 엔진)**
- 명확한 규칙으로 수치를 산출
- 예: "RPE 9 → 무게 -5kg", "1RM 100kg의 70% = 70kg", "User 가용 장비로 필터링"
- 결정적, 빠름, 단위 테스트 가능. LLM 개입 없음

**Layer 3 — Expression (LLM)**
- 엔진이 산출한 결정을 페르소나 톤으로 변환
- 예: 같은 "5kg 감소" 결정도 강성/부드러움/분석형 페르소나마다 다르게 표현
- 결정 자체는 변하지 않음. 표현만 LLM이 담당

## 고려한 대안

### 대안 A: LLM 단독
- 모든 결정을 LLM에게 위임
- **기각 이유**: 동일 입력에 다른 출력이 나올 수 있어 테스트 불가. 도메인 규칙(예: "User가 보유하지 않은 장비 사용 금지")을 LLM이 매번 기억해야 함. 인-세션 응답 지연.

### 대안 B: 엔진 단독
- 모든 결정을 룰/ML 모델로 처리
- **기각 이유**: "왜 이 결정을 내렸는지"를 사용자에게 설명하기 어려움. 페르소나별 톤 변환을 엔진으로 표현하는 것은 부자연스러움. 신규 상황(예: 코로나 후 재활)에 룰을 매번 추가해야 함.

## 결과

- LLM이 도메인 규칙을 우회할 수 없음 → 안전성 확보
- 엔진은 단위 테스트 가능 → 회귀 방지
- LLM은 표현과 추론에만 집중 → 응답 품질 향상
- LLM 호출이 결정 후에만 발생 → 비용/지연 최적화

## 트레이드오프

- LLM과 엔진 사이의 인터페이스(스키마)를 명확히 정의해야 함. 정책이 "뭘 할지"를 산출하면, 엔진이 "어떻게 할지"를 채워야 함. 이 경계가 흐려지면 두 레이어의 책임이 섞임.
- LLM이 정책을 결정할 때 필요한 컨텍스트(과거 이력, 추세 등)를 어떻게 전달할지 추가 결정 필요.
